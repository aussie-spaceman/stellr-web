## Correction — the migration was applied twice

Step 3 above records an apply at 21 Sept 22:51Z with the ledger realigned to
`20260921120000`. On 22 Sept ~14:20Z, before merging, `npm run db:status -- --prod`
listed `20260921120000` as **PENDING** (160 ledger rows), so this session applied
it again through the Supabase MCP. The SQL is idempotent throughout
(`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `ON CONFLICT DO NOTHING`),
and the result is correct: `credentials` and `credential_events` exist with RLS,
`credentials` holds **2** rows against `training_certificates`' 2 — no duplicate
backfill. Afterwards the ledger is 161 rows, `20260921120000` is no longer pending,
and a stray MCP-timestamp row `20260922142559` sits in ledger-only.

Why the two readings disagree was not established. **Do not assume a realignment
held — re-read `db:status -- --prod` after it.** The stray row is cosmetic, the
same class as the TRACKER 4.8 pair; deleting it is a separate, explicit step.

This also came out of two sessions promoting the same `dev` concurrently (this
record and PR #134 from one, PR #133 from the other). See the memory note
