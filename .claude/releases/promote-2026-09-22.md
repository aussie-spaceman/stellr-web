- **Runtime code — one behavioural change, and it is a guard:**
  `assertLiveCredentials()` (DocuSign issuance, Stripe checkout, Checkr orders,
  Clerk provisioning) was armed by `VERCEL_ENV === 'production'` alone. It is
  now armed by `isRealProductionApp()` = that **and**
  `NEXT_PUBLIC_APP_ENV !== 'dev'`.

  - Unset, misspelt, or any value other than the literal `dev`: **still armed**
    (four unit tests pin this, including the missing-variable case that caused
    the June–September sandbox-envelope incident).
  - On the `stellr-web-dev` project, whose own production target builds `dev`:
    now correctly disarmed, which is the point of #138 — it was returning 503
    on the Checkr order route, the one place background-check certification can
    be exercised.

    list stops crying wolf on dev. Admin-only route; production output unchanged.

## Open / not verified

- **`NEXT_PUBLIC_APP_ENV` on the production Vercel project was not read
  directly in this session.** The Vercel connector returns 403 for
  `projectEnvVars`; the cron probe checks the shared secret first so an
  unauthenticated call cannot reveal it; runtime-log queries for the cron
  windows hit `ExceedsBillingLimitError`. The value matters because it is the
  only input that can disarm the sandbox guard.
  Indirect evidence that it is `prod`: the 10 Sept confirmation by exercising a
  cron guard with the secret, and the fact that `APP_ENV=dev` on production
  would make `guardCron` skip **all fourteen crons** — membership expiry,
  reminders, drips — which would be conspicuous. If it somehow were `dev`,
  production would already be broken in a larger way than this promotion.
  **Cheap post-deploy check:** open `/api/admin/health/integrations` as an
