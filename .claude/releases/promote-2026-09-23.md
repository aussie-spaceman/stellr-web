## Migration — apply to production BEFORE merge

`db:status --prod` (23 Sept) lists `20260923120000` as pending. The two 10 Sept files are the known
MCP-timestamp pair — **do not re-apply**.

```sql
ALTER TABLE public.event_refunds
  ADD COLUMN IF NOT EXISTS source   text NOT NULL DEFAULT 'admin',
  ADD COLUMN IF NOT EXISTS note     text,
  ADD COLUMN IF NOT EXISTS currency text;

DO $$ BEGIN
  ALTER TABLE public.event_refunds
    ADD CONSTRAINT event_refunds_source_check CHECK (source IN ('admin', 'stripe_external'));
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;

CREATE UNIQUE INDEX IF NOT EXISTS event_refunds_stripe_refund_id_key
  ON public.event_refunds (stripe_refund_id);
```

Additive. Old code ignores the new columns, and existing rows get `source='admin'`. If production
held a duplicate `stripe_refund_id`, the unique index would fail. The migration runs as one
transaction, so it would roll back with nothing changed.
