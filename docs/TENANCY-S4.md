# Tenancy S4: database-enforced isolation

Stage 4 of the multi-tenancy plan, first lane: the spike and its decision, the tenant role and policies, `tenantDb()`, the Storage rule, and the cross-tenant pgTAP matrix. The decision and its evidence are in `docs/S4-SPIKE.md` (Option B).

**Nothing on a live flow changes.** Registration, check-in, payments, e-sign, uploads and community all still run as `service_role`, which bypasses RLS. The new policies apply to `tenant_app` only, and nothing in the app connects as `tenant_app` yet: S5 wires that up.

## What S4 adds

| Piece | Where | What it does |
|---|---|---|
| `tenant_app` role | `20261104200000_tenant_isolation_policies.sql` | NOLOGIN, NOINHERIT, NOBYPASSRLS. Nobody is a member yet. The migration refuses to continue if a role of that name already exists with an attribute that escapes RLS. |
| `public.app_tenant_id()` | same | The tenant pinned for this transaction (`stellr.tenant_id`), or NULL. NULL matches no row, so it fails closed. STABLE, SECURITY INVOKER, and called as `(SELECT …)` so it runs once per query. |
| Tenant policies on 35 tables | same | Every registry table with its own `tenant_id` (`own` or `derived`) gets `tenant_isolation` (PERMISSIVE) and `tenant_isolation_guard` (RESTRICTIVE), both `TO tenant_app` only, plus the four DML grants. The guard means a later `TO PUBLIC` policy cannot widen a tenant's view. |
| `public.tenants` own row | same | `tenant_app` may SELECT its own tenant row, and nothing else. |
| `public.storage_object_tenant_id(path)` | `20261104210000_storage_tenant_prefix.sql` | The tenant owning a Storage path: `{tenant_id}/…` belongs to that tenant if the tenant exists, anything else is Stellr's. SECURITY DEFINER (it must see every tenant id) and sealed. |
| `tenantDb(tenantId)` | `lib/tenancy/db.ts` | The only code that runs as `tenant_app`. It throws without a tenant, binds every value, refuses SQL that could change role or tenant, and reads the pin back. Off unless `TENANT_DB_ENABLED=true` and a driver is registered. Neither is set or registered in the app. |
| Allow-list | `lib/tenancy/db-callers.ts` | Every importer of `lib/tenancy/db`. `lib/tenancy/db.test.ts` fails on any other. |
| Storage paths | `lib/tenancy/storage.ts` | `tenantObjectPath()` for new objects, `objectTenantId()` with the same rule as the SQL function. |
| Cross-tenant matrix | `supabase/tests/database/tenant_isolation.test.sql` | Generated by `scripts/gen-tenant-isolation-pgtap.mjs` from the registry. Runs in CI's `db` job. |
| Lint | `scripts/check-migration-tenancy.mjs` | `npm run lint:migrations` now also fails when an `own`/`derived` table lacks either tenant policy. |
| FORCE readiness check | `supabase/tests/tenancy_force_rls_readiness.sql` | Read-only, run by hand. |

## How a tenant transaction runs

```sql
BEGIN;
SET LOCAL ROLE tenant_app;
SELECT set_config('stellr.tenant_id', '<tenant uuid, lower case>', true);
SELECT current_user AS role, public.app_tenant_id()::text AS tenant;  -- tenantDb checks both
-- caller's statements, values bound as $1, $2, …
COMMIT;
```

Both settings are transaction-local, so a pooled connection never carries a tenant into the next request.

Inside the transaction, `tenant_app`:

- sees only rows whose `tenant_id` matches;
- cannot insert a row for another tenant. On derived tables the trigger derives the tenant from the event, then RLS checks it;
- cannot move its own row to another tenant: RLS refuses it on `own` tables, and the trigger rewrites it from the event on `derived` tables;
- has no privilege at all on the `via_parent` child tables (`participants`, `agreement_recipients`, …) until they get their own `tenant_id`.

## The cross-tenant matrix

`scripts/gen-tenant-isolation-pgtap.mjs` holds a fixture for every tenant table, and generation fails if a tenant table has no fixture. It seeds Stellr and a canary tenant with rows in all 35 tables. Then, as `tenant_app` with each tenant pinned in turn, it asserts:

- the context sees 0 of the other tenant's rows and exactly its own;
- UPDATE and DELETE of the other tenant's rows touch 0;
- INSERT of an other-tenant row fails with 42501;
- an own-tenant INSERT works, so the policies are not just deny-all;
- with no tenant pinned, or garbage pinned, it sees and writes nothing;
- afterwards, as the owner, each tenant has exactly its rows: no row moved and none was deleted.

Every count is checked against the owner's own count, so no assertion can pass on an empty table.

**When you add a tenant table:**

1. Classify it in `lib/tenancy/registry.ts`.
2. In its migration, write the same policy block as `20261104200000`: the four GRANTs to `tenant_app`, then `tenant_isolation` and `tenant_isolation_guard`.
3. Add a fixture to `FIXTURES` in the generator.
4. Regenerate with `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/gen-tenant-isolation-pgtap.mjs`.

`lib/tenancy/isolation.test.ts` and `npm run lint:migrations` fail until all four are done.

## FORCE RLS: the later step

This lane deliberately sets **no** `FORCE ROW LEVEL SECURITY`.

- **Option B does not need it.** FORCE only changes what a table's **owner** sees. `tenant_app` owns no table, so the RLS already enabled on every table binds it. The matrix proves that.
- **It could break live flows if the owner lacks BYPASSRLS.** Several SECURITY DEFINER functions owned by `postgres` read tenant tables:
  - `tenancy_derive_tenant_id()` reads `public.events`;
  - `can_read_space()` and `can_read_chat_channel()` gate Realtime chat;
  - `rename_event_slug()` and the event-slug inventory;
  - the survey functions;
  - the entitlements cohort functions.

  On the hosted project, `postgres` is not a superuser. Whether it has BYPASSRLS cannot be read from this repo, and CI's local database (where `postgres` is a superuser) would hide the difference. Rehearsed with an owner lacking BYPASSRLS, FORCE on `events` made the derivation trigger silently stamp a canary-event registration with Stellr's tenant (`docs/S4-SPIKE.md`, §6).

**Before anyone writes the FORCE migration:**

1. **Owner:** run `supabase/tests/tenancy_force_rls_readiness.sql` on dev, then production, in the SQL editor. Run it as the role migrations run as, outside event hours.
2. Section A must show `postgres | rolbypassrls = true`. Section C must show `owner_bypasses_rls = true` on every row. Section C finds functions by table name in their source, so it misses functions that build SQL dynamically, such as `rename_event_slug()`. Review those by hand.
3. If both hold, the FORCE migration is one `ALTER TABLE public.<t> FORCE ROW LEVEL SECURITY;` per tenant table. Do the same for the `via_parent` tables once they have `tenant_id`. Update the generator's FORCE assertion in the same PR. Apply it outside event hours, never within 72 hours of a live event, and re-run the matrix.
4. If `postgres` lacks BYPASSRLS, FORCE needs a policy for each definer function's owner first. That is its own design (it reopens the definer review), and FORCE waits for it.

## Storage

- **New objects for a tenant** go under `{tenant_id}/…` in their bucket. Build the path with `tenantObjectPath(tenantId, path)`. It refuses a path that already starts with an id, so a caller cannot smuggle another tenant's prefix in.
- **Existing objects stay where they are** and are Stellr's by policy. Nothing is moved. Legacy paths can start with a uuid of their own (`{member_id}/…`), so a first segment counts as a tenant only when it is a real tenant id.
- **No storage.objects policy is created in this lane.** Every bucket is private, and the app reaches Storage only with the secret key, through signed URLs. `storage.objects` also belongs to the Storage service's role, so whether the migration role may add policies is an owner check (readiness section E). When the first tenant upload ships (S5), the policy per bucket is:

```sql
CREATE POLICY tenant_objects ON storage.objects AS PERMISSIVE FOR ALL TO tenant_app
  USING (bucket_id = '<bucket>' AND public.storage_object_tenant_id(name) = (SELECT public.app_tenant_id()))
  WITH CHECK (bucket_id = '<bucket>' AND public.storage_object_tenant_id(name) = (SELECT public.app_tenant_id()));
```

## Rehearsal (before applying anywhere)

Both migrations are additive: no table, no data change, no FORCE, and no grant to any role the app connects as.

1. Apply on a scratch database built the CI way (`docs/RUNBOOK-ci-database.md`), then run `supabase test db supabase/tests/database`. All three files must pass.
2. This lane did that on Postgres 17 (PGlite). It also applied both migrations as a non-superuser owner with CREATEROLE, and re-applied them, which was a no-op. It has not run on a production restore.
3. **Do not apply on 6 Nov (Nevada)**, nor within 72 hours of a live event, even though no live query is affected. Apply to dev first through the usual migration path, then to production through the Production migration Action.

## Owner actions

1. **Apply** `20261104200000` and `20261104210000` to dev, then production, after the rehearsal. Not on an event day.
2. **Run the readiness check** (`supabase/tests/tenancy_force_rls_readiness.sql`) on both projects and record:
   - A: does `postgres` have BYPASSRLS?
   - C: does every definer owner bypass RLS?
   - E: can the migration role add policies to `storage.objects`?

   These answers decide the FORCE step and where the S5 storage policies are created.
3. **S5, not now: the tenant login.** In the SQL editor, as `postgres` (a non-superuser can do this; rehearsed):

   ```sql
   CREATE ROLE tenant_app_login LOGIN NOINHERIT PASSWORD '<generated, at least 32 random bytes>';
   GRANT tenant_app TO tenant_app_login;
   ```

   - Store the pooler connection string in Vercel as a server-only secret, never `NEXT_PUBLIC_`. Use transaction mode (port 6543) and the user `tenant_app_login.<project-ref>`.
   - Never print or commit the password.
   - Set `TENANT_DB_ENABLED=true` only when S5's first converted route ships.
4. **Confirm** the pooler's client limit on the project's plan page (`docs/S4-SPIKE.md`, §2).
