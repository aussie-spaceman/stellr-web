# Tenancy S4: database-enforced isolation

Stage 4 of the multi-tenancy plan, first lane: the spike and its decision, the tenant role and policies, `tenantDb()`, the Storage rule, and the cross-tenant pgTAP matrix. The decision and its evidence are in `docs/S4-SPIKE.md` (Option B).

**Nothing on a live flow changes.** Registration, check-in, payments, e-sign, uploads and community all still run as `service_role`, which bypasses RLS. The new policies apply to `tenant_app` only, and nothing in the app connects as `tenant_app` yet: S5 wires that up.

## How a tenant transaction runs

```sql
BEGIN;
SET LOCAL ROLE tenant_app;
SELECT set_config('stellr.tenant_id', '<tenant uuid, lower case>', true);
SELECT current_user AS role, public.app_tenant_id()::text AS tenant;  -- tenantDb checks both
-- caller's statements, values bound as $1, $2, …
COMMIT;
```

Both settings are transaction-local, so a pooled connection never carries a tenant into the next request.

Inside the transaction, `tenant_app`:

- sees only rows whose `tenant_id` matches;
- cannot insert a row for another tenant. On derived tables the trigger derives the tenant from the event, then RLS checks it;
- cannot move its own row to another tenant: RLS refuses it on `own` tables, and the trigger rewrites it from the event on `derived` tables;
- has no privilege at all on the `via_parent` child tables (`participants`, `agreement_recipients`, …) until they get their own `tenant_id`.

## What tenant_app may write

Two rules sit on top of "rows of its own tenant". Both are in `lib/tenancy/tenant-role.ts` and are checked by the matrix.

- **Routing, ownership and role tables are read-only.** `tenant_app` may read its own rows of `events`, `tenant_domains` and `tenant_memberships`, and nothing more. Without this rule a tenant could do three things:
  - insert an event with a slug another tenant will use. Slugs are globally unique, and `tenancy_derive_tenant_id()` finds a row's tenant by its slug, so the other tenant's later registrations would be stamped with the squatter's tenant;
  - claim any host in `tenant_domains`, the table S5 routes Host to tenant from;
  - grant itself, or anyone, the `owner` role.

  Platform code (service role) writes these tables.
- **A row may point only at its own tenant's rows.** The guard's WITH CHECK checks two things on every write:
  - the row's event key names an event its tenant has (or is NULL, on tables where it is optional);
  - every foreign key to a tenant table names a row `tenant_app` can see. RLS on the parent table limits that to the tenant's own rows.

  A tenant therefore cannot attach a join token to another tenant's registration, or an assignment to another tenant's module. It cannot learn whether another tenant's id exists either: RLS refuses before the foreign-key check could answer with 23503. A key to a `via_parent` table must be NULL until that table has its own `tenant_id`. The matrix checks `TENANT_PARENT_REFS` against the real foreign keys, so a new foreign key between tenant tables fails the `db` job until it is listed and guarded.

- **Some tables with a `tenant_id` are platform-level, and `tenant_app` gets nothing on them.** `platform_audit_events` (the hash-chained audit, written by `lib/audit/platform.ts`) and `tenant_data_keys` (wrapped field-encryption keys, read by `lib/field-crypto-store.ts`) are classified `platform` in the registry and listed in `TENANT_APP_NO_ACCESS_TABLES` with the reason. They get no tenant policy and no grant; the matrix asserts `tenant_app` holds no privilege on either, and `lib/tenancy/isolation.test.ts` fails when another non-tenant table with a `tenant_id` is not listed.

## What tenantDb does and does not stop

`tenantDb` is how S5 server code will act as one tenant. It assumes the code calling it is reviewed code in an allow-listed file. Request data reaches it only as bound values.

- **Only statements `tenantSql` built reach the driver.** They are frozen and recorded in a module-private WeakSet, so a hand-made `{ text, values }` is refused.
- **Values are always bound.** A value can become SQL only through a function that runs SQL text, and those are refused.
- **The caller's SQL is checked as text.** It must be one plain DML or read statement, with no comments and no `U&` escapes. It must not mention `set_config`, `pg_settings`, the `*_to_xml` family, `ts_stat` or `ts_rewrite` in any spelling, quoted or schema-qualified included.
- **The pin is read back after every statement, before any row is returned.** If a statement moved the tenant or the role, by a path the text check does not know, `tenantDb` throws, and the whole transaction rolls back with its writes.
- **What remains:** a path the text check does not know that re-pins and restores the pin within one statement. Reaching that needs SQL written into an allow-listed file, not request data. If the role is dropped (`role = none`), the transaction falls back to the S5 login, `tenant_app_login`, which is NOINHERIT and holds no table grant of its own. So it fails closed, and the read-back catches it anyway.

## The cross-tenant matrix

`scripts/gen-tenant-isolation-pgtap.mjs` holds a fixture for every tenant table, and generation fails if a tenant table has no fixture. It seeds Stellr and a canary tenant with rows in all 35 tables. Then, as `tenant_app` with each tenant pinned in turn, it asserts:

- the context sees 0 of the other tenant's rows and exactly its own;
- UPDATE and DELETE of the other tenant's rows touch 0;
- INSERT of an other-tenant row fails with 42501;
- an own-tenant INSERT works, so the policies are not just deny-all (except on the three read-only tables, where INSERT, UPDATE and DELETE of its own rows are refused);
- a row pointing at the other tenant's parent row, at an id that does not exist, or at an event its tenant does not have, is refused; the same row pointing at its own parent works;
- with no tenant pinned, or garbage pinned, it sees and writes nothing;
- afterwards, as the owner, each tenant has exactly its rows: no row moved and none was deleted.

Every count is checked against the owner's own count, so no assertion can pass on an empty table.

**When you add a tenant table:**

1. Classify it in `lib/tenancy/registry.ts`.
2. If it has a foreign key to another tenant table, list it in `TENANT_PARENT_REFS` (`lib/tenancy/tenant-role.ts`). If platform code alone writes it, add it to `TENANT_APP_READ_ONLY_TABLES`.
3. In its migration, write the same policy block as `20261104200000`: the GRANTs to `tenant_app`, then `tenant_isolation` and `tenant_isolation_guard`. Take the guard's WITH CHECK from `guardWithCheck()`.
4. Add a fixture to `FIXTURES` in the generator.
5. Regenerate with `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/gen-tenant-isolation-pgtap.mjs`.

`lib/tenancy/isolation.test.ts`, `npm run lint:migrations` and the `db` job fail until all five are done.

## FORCE RLS: the later step

This lane deliberately sets **no** `FORCE ROW LEVEL SECURITY`.

- **Option B does not need it.** FORCE only changes what a table's **owner** sees. `tenant_app` owns no table, so the RLS already enabled on every table binds it. The matrix proves that.
- **It could break live flows if the owner lacks BYPASSRLS.** Several SECURITY DEFINER functions owned by `postgres` read tenant tables:
  - `tenancy_derive_tenant_id()` reads `public.events`;
  - `can_read_space()` and `can_read_chat_channel()` gate Realtime chat;
  - `rename_event_slug()` and the event-slug inventory;
  - the survey functions;
  - the entitlements cohort functions.

  On the hosted project, `postgres` is not a superuser. Whether it has BYPASSRLS cannot be read from this repo, and CI's local database (where `postgres` is a superuser) would hide the difference. Rehearsed with an owner lacking BYPASSRLS, FORCE on `events` made the derivation trigger silently stamp a canary-event registration with Stellr's tenant (`docs/S4-SPIKE.md`, §6).

**Before anyone writes the FORCE migration:**

1. **Owner:** run `supabase/tests/tenancy_force_rls_readiness.sql` on dev, then production, in the SQL editor. Run it as the role migrations run as, outside event hours.
2. Section A must show `postgres | rolbypassrls = true`. Section C must show `owner_bypasses_rls = true` on every row. Section C finds functions by table name in their source, so it misses functions that build SQL dynamically, such as `rename_event_slug()`. Review those by hand.
3. If both hold, the FORCE migration is one `ALTER TABLE public.<t> FORCE ROW LEVEL SECURITY;` per tenant table. Do the same for the `via_parent` tables once they have `tenant_id`. Update the generator's FORCE assertion in the same PR. Apply it outside event hours, never within 72 hours of a live event, and re-run the matrix.
4. If `postgres` lacks BYPASSRLS, FORCE needs a policy for each definer function's owner first. That is its own design (it reopens the definer review), and FORCE waits for it.

## Storage

- **New objects for a tenant** go under `{tenant_id}/…` in their bucket. Build the path with `tenantObjectPath(tenantId, path)`. It refuses a path that already starts with an id, so a caller cannot smuggle another tenant's prefix in.
- **Existing objects stay where they are** and are Stellr's by policy. Nothing is moved. Legacy paths can start with a uuid of their own (`{member_id}/…`), so a first segment counts as a tenant only when it is a real tenant id.
- **The rule is enforced in server code, not in a `storage.objects` policy.** Every request to Storage goes through the Storage HTTP API. That API runs as the role carried by its key or JWT:
  - `service_role` for the secret key the app uses. It has BYPASSRLS, so no policy applies;
  - `anon` or `authenticated` for a browser. No browser reaches Storage directly today: every bucket is private and reads go through server-signed URLs.

  No request runs as `tenant_app`, so a policy `TO tenant_app` would never bind. (An earlier draft of this runbook proposed one; a review caught it.) So in S5:
  - tenant upload code builds every object path with `tenantObjectPath(tenantId, path)`;
  - it checks every path it signs, reads, replaces or deletes with `assertTenantObjectPath(tenantId, path)`, which throws for a legacy path or another tenant's folder.
- **A database backstop is possible but not built here.** A BEFORE INSERT trigger on `storage.objects` could refuse a new object outside its tenant's folder even for `service_role`. It would sit on every live upload, and the migration role may not own `storage.objects` (readiness section E). It is an S5 decision for the owner, not something to slip in before Nevada.
- **`public.storage_object_tenant_id()`** gives the same answer in SQL, for server-side audits and listings. Only `tenant_app` and `service_role` may execute it. A browser-facing policy, if one is ever needed, needs its own design: Clerk tokens carry no tenant claim.
- No `storage.objects` policy is created or changed in this lane.

## Rehearsal (before applying anywhere)

Both migrations are additive: no table, no data change, no FORCE, and no grant to any role the app connects as.

1. Apply on a scratch database built the CI way (`docs/RUNBOOK-ci-database.md`), then run `supabase test db supabase/tests/database`. All three files must pass.
2. This lane did that on Postgres 17 (PGlite). It also applied both migrations as a non-superuser owner with CREATEROLE, and re-applied them, which was a no-op. It has not run on a production restore.
3. **Do not apply on 6 Nov (Nevada)**, nor within 72 hours of a live event, even though no live query is affected. Apply to dev first through the usual migration path, then to production through the Production migration Action.

1. **Apply** `20261104200000` and `20261104210000` to dev, then production, after the rehearsal. Not on an event day.
2. **Run the readiness check** (`supabase/tests/tenancy_force_rls_readiness.sql`) on both projects and record:
   - A: does `postgres` have BYPASSRLS?

